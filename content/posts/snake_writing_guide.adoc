== Why Another snake_case Utility?

// THE DISTINCTION:
// Conventional snake_case conversion is primarily a string
// transformation. Real-world filenames need more thoughtful
// normalization.
//
// Explain why repeatedly constructing rename expressions
// became less appealing than writing a reusable Bash function.

// CENTRAL ARGUMENT:

// It's filenames that are genuinely pleasant to work with.

Consolidated feature list:
- Extension-aware snake conversion. Real extensions are split and normalized; suffixes go before the extension; extensionless files and names ending in a period remain a single base name.
- Mixed and repeated separator normalization. Spaces, hyphens, brackets, punctuation, and rejected periods become underscores before runs are collapsed:
- a___b → a_b
- a-_b → a_b
- a-_.b → a_b by default
- With -p, periods stay protected: a_._b → a_._b, and repeated periods collapse to one.
- Collision-safe by default. Existing targets get an incrementing _N suffix rather than being silently replaced.
- Explicit overwrite semantics. -o replaces target files; for existing directories it moves the source inside under its transformed name, such as my_dir/my_dir, and keeps descending with that name on further collisions.
- Recursive and current-directory modes. -r processes trees and propagates active flags; omitted path, ., or ./ processes current-directory entries. Recursive merges also process the moved source contents.
- Case-insensitive filesystem correctness. Case-only renames are not treated as collisions, avoiding spurious _N suffixes on macOS.
- Predictable cleanup. Apostrophes are removed, trailing separators are stripped, and already-correct names are no-ops.
- Domain-specific implementation. Bash/Zsh function with no Perl dependency, and no regex-escaping burden for routine normalization.
Tradeoff: unlike Perl rename, it is not a general-purpose arbitrary regex renamer.
