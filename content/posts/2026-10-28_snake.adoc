== The Problem

If you work in the command line chances are you hate filenames with spaces in them; don't even get me started on awkward punctuation and inconsistent capitalization!

A file like: `My Important Document - Final Version (2).pdf`

\...means I'm either going to have to quote it: `vi 'My Important Document - Final Version (2).pdf'`

\...or even more horribly, escape it: `vi My\ Important\ Document\ \-\ Final\ Version\ \(2\).pdf`

If you are writing a bash script? Then you have to think about...

* _Word splitting_ because you forgot to quote `$file` which can split a file name into multiple arguments, unintentionally.
* Unexpected _globbing_ will lead you astray because `*`, `?`, or `[...]` means something very different to the shell than it does to the user writing it in a file name and
* did you know that unix thinks new lines are perfectly acceptable in a file name even though I can't think of one single use case why you would want to do this!?!

All these and more makes the possibility of your scripts unexpectedly falling over an increasingly possible and this could all be avoided if filenames were just house-trained better.

Given this typographical hellscape, who are the villains committing these sins of syntax? Well, it isn't me! `this_is_my_file_csw_v1.adoc` is about as adventurous as I get. It's `You’re unsubscribed..eml` when I copy a file from email to my file system so I can actually refer to it again when I need it or, it's some file I've downloaded (`Old Paper Texture.jpg`) or an applications has generated it -- `Bogos Data/WORD TEMPLATES/Basic Report Template.doc` - I feel like the Kyle Reece of the command line dodging overtly verbose Hunter-Killers in the sky.

Now, I say this knowing that I should write my bash scripts to take all of these things into consideration because decrying what I consider to be poor filename etiquette doesn't mean that I'm not going to still encounter it.

I think it's more that when I see it, I have to do something about it.

== My Solution

I like my files in `snake_case`.

There are tools like `rename` that can do this. If your file name is `Hello World.txt`

[source,bash]
----
rename -n 's/ /_/; y/A-Z/a-z/' "Hello World.txt"
----

\... will get you to `hello_world.txt`. However, it requires a knowledge of _regex_ and we all know how that goes. Also, `rename` is the Swiss Army Knife of file renaming and I thought it might be a little more than my needs required.

All I want are my files to be in `snake_case`. In my naivety I thought _bash parameter expansion_ was probably all I needed and with a child's enthusiasm, my `snake` function was born.

[source,bash]
----
snake() {
    local file="$1"
    local result
    result="${file// /_}" # Replace spaces with underscores
    result="${result,,}" # convert everything to lower case.
    mv -- "$file" "$result"
    echo "Renamed '$file' to '$result'"
}
----

== Scope Creep

.Gah, brackets!
[source,bash]
----
snake 'My Important Document - Final Version (2).pdf'
Renamed 'My Important Document - Final Version (2).pdf' to './my_important_document_final_version_(2).pdf'
----


Over time, it turns out that my interpretation of snake case is a lot more nuanced than I thought. I don't like punctuation (except when I want a directory to be `name.status.date`). I don't like special characters like apostrophes or trailing spaces. I want to batch process a lot of files at once, I want that batch process to be recursive, except when I don't and I don't want it to accidentally to overwrite files when I have `Hello World.txt` and `hello_world.txt` together.

With each new file I renamed I found that the creativity of cyberland had found yet another way to disturb my filename namaste and my snake because an uroboros.

As of writing `snake` has an expanded feature list that addresses most of the file naming issues I've encountered so far. Below, highlights the key file calming features I find most restful. No doubt the list will continue to grow as the file pixies continue to conspire against me.

.Feature List
[cols="1,1",options="header"]
|===
|Making filenames behave |Making the function useful

a|
* Converts files and directories to lowercase `snake_case`.
* Replaces spaces, punctuation, brackets and other awkward characters.
* Collapses repeated or mixed separators:
** `a-_.b` → `a_b`
** `a___b` → `a_b`
* Optionally preserves periods, for those times when they actually mean something.

a|
* Handles multiple files and directories in one go.
* Can work recursively through directory trees.
* Understands filename extensions.
* Avoids overwriting existing files by adding numbered suffixes.
* Allows overwriting when explicitly requested.
* Includes command-line options and built-in help.

|===

== In Conclusion

What started as a simple exercise in snake case quickly ballooned into complex set of requirements that were nothing short of a highly opinionated filename renaming utility with its own curated views about punctuation, extensions, recursion and what constitutes acceptable behaviour.

How many bells are ringing here? Was this your last customer engagement, software development, sales pursuit or hasty promise to your spouse?

How often have we heard, or indeed said, "It should be simple enough"? The trouble is that the simplicity usually exists only because we haven't yet encountered all the exceptions, edge cases and unforeseen consequences. It's only when you get your hands dirty that you discover the solution you wanted was the solution you needed.

That is why we should always understand our problem statement, clearly define our use cases and modelled our target states _before_ we begin lest our seemingly trivial requirement becomes a considerably large, more expensive and more time consuming undertaking that we could have possibly imagined.

All I wanted to do was to get rid of some spaces.
